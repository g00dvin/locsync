# Исследование: USB GNSS-приёмник как второй источник данных клиента

Цель — дать клиенту (магнитоле) два режима работы:

1. **Сервер** — как сейчас: координаты приходят от телефона по UDP.
2. **USB** — координаты берутся с GNSS-приёмника, подключённого к магнитоле по USB.

Вторая цель — поддержать как можно больше USB-приёмников без root.

---

## 1. Что такое «USB GPS» с точки зрения Android

Почти все потребительские USB GNSS-приёмники — это **последовательный порт
поверх USB**, по которому модуль непрерывно выдаёт текст **NMEA 0183**
(иногда ещё и бинарный протокол производителя). Различаются они только тем,
*как* реализован последовательный порт:

| Класс устройства | Чип / пример | VID:PID | Как читать |
|---|---|---|---|
| **Нативный CDC-ACM** | u-blox 5/6/7/8/M9/M10/F9 (VK-162, VK-172, Navilock NL-8xxx, simpleRTK2B), STM32 VCP, CH9102, многие Quectel | `1546:01a5…01a9` (u-blox), `0483:5740` (ST), `1a86:55d4` (CH9102) | Стандартный класс USB CDC — драйвер по дескрипторам интерфейса, VID/PID не важен |
| **Prolific PL2303** | GlobalSat BU-353S4/N, много «SiRF»-мышек | `067b:2303`, `067b:23a3…23f3` | Вендорный протокол настройки, нужен драйвер |
| **Silicon Labs CP210x** | модули SparkFun/Adafruit, Quectel L76/LC29H на платах | `10c4:ea60`, `ea70`, `ea71` | Вендорный драйвер |
| **FTDI** | промышленные/RTK-приёмники, самодельные | `0403:6001`, `6010`, `6011`, `6014`, `6015` | Вендорный драйвер |
| **WCH CH340/CH341** | дешёвые китайские модули (NEO-6M/7M/8M + адаптер, ATGM336H, BN-xxx) | `1a86:7523`, `1a86:5523` | Вендорный драйвер |
| LTE-модемы с NMEA-портом | Quectel EC2x/EG25, Fibocom | разные | Отдельный интерфейс модема; GPS обычно надо включить AT-командой (`AT+QGPS=1`) |
| **Не поддерживается** | Garmin GPS 18x USB (`091e:*`) — собственный бинарный протокол Garmin; SiRF-приёмники в режиме SiRF binary без переключения в NMEA | — | Отдельная реализация, не стоит затрат |

Вывод: если поддержать **CDC-ACM + PL2303 + CP210x + FTDI + CH34x** и
**NMEA 0183**, это покрывает практически весь рынок USB GNSS-«мышек» и модулей.

## 2. Варианты доступа к USB на Android

### Вариант A — Android USB Host API + userspace-драйвер (рекомендуется)

`android.hardware.usb.UsbManager` → `UsbDeviceConnection` → bulk-передачи.
Драйвер последовательного порта реализуется в приложении, ядерные модули не
нужны, root не нужен. Работает на любом устройстве с USB host (а это все
Android-магнитолы).

Готовая библиотека: **[mik3y/usb-serial-for-android](https://github.com/mik3y/usb-serial-for-android)**
(лицензия MIT — совместима с GPLv3 проекта; актуальная версия на момент
исследования — `3.11.0`, распространяется через JitPack):

```groovy
// settings.gradle → dependencyResolutionManagement.repositories
maven { url 'https://jitpack.io' }
// client-app/build.gradle
implementation 'com.github.mik3y:usb-serial-for-android:3.11.0'
```

Встроенный `UsbSerialProber` содержит драйверы:
`CdcAcmSerialDriver`, `Cp21xxSerialDriver`, `FtdiSerialDriver`,
`ProlificSerialDriver`, `Ch34xSerialDriver`, `GsmModemSerialDriver`.
Важно: **CDC-ACM определяется по дескрипторам интерфейса**, а не по
таблице VID/PID — значит любой приёмник с нативным USB (u-blox, ST, CH9102,
неизвестные клоны) подхватится без доработок. Для вендорных чипов с
нестандартным VID/PID есть `ProbeTable` — можно добавить свои пары или дать
пользователю выбрать драйвер вручную.

Плюсы: без root, весь рынок чипов, автоматическое отсоединение ядерного
драйвера (`claimInterface(iface, true)`), есть событие подключения для автозапуска.
Минусы: нужен диалог разрешения USB (решается, см. §5), +1 зависимость.

### Вариант B — читать `/dev/ttyACM0` / `/dev/ttyUSB0` напрямую

Работает только если ядро магнитолы собрано с `cdc_acm`/`pl2303`/`ch341`/…,
и только с root или ослабленной SELinux (у обычного приложения нет прав на
`/dev/tty*`). Многие китайские магнитолы рутованы, но полагаться на это
нельзя. Имеет смысл максимум как скрытая «экспертная» опция позже.

### Вариант C — встроенный GNSS HAL / «внешний GPS» в прошивке

Некоторые прошивки (FYT и др.) умеют сами брать GPS с USB/UART, но это
не управляется из приложения и зависит от модели. Не наш путь.

**Решение: вариант A.**

## 3. Протоколы данных

### 3.1 NMEA 0183 (обязательно, универсально)

Нужные предложения (talker-префикс любой: `GP`, `GL`, `GA`, `GB`/`BD`, `GQ`, `GN`):

| Предложение | Что берём |
|---|---|
| `RMC` | время UTC + **дата**, статус `A/V`, широта/долгота, скорость (узлы → м/с ×0.514444), курс |
| `GGA` | качество фикса (0 = нет, 1 = GPS, 2 = DGPS, 4/5 = RTK), число спутников в решении, **HDOP**, высота MSL + геоид |
| `GST` | СКО широты/долготы в метрах → **честная горизонтальная точность** (есть у u-blox, Quectel, MTK) |
| `GSA` | PDOP/HDOP/VDOP, режим 2D/3D |
| `GSV` | спутники в видимости и SNR → `SatelliteBarsView` |
| `VTG` | курс/скорость, если нет в RMC |

Особенности, которые нужно учесть в парсере:

- **Проверка контрольной суммы** `*hh` обязательна — по ней же автоопределяется скорость порта.
- **Группировка по эпохам**: все предложения одной эпохи имеют одинаковое время UTC.
  Фикс публикуется, когда эпоха закончилась (пришло предложение со следующим
  временем или получены RMC+GGA текущей).
- **Точность**: если есть `GST` — `accuracy = sqrt(σlat² + σlon²)` (≈ CEP68 при
  эллипсе, близком к кругу). Если нет — оценка `HDOP × UERE`, где UERE ≈ 4–5 м
  (настраиваемая константа), с нижней границей ~2 м.
- **Курс на малой скорости**: при скорости < ~0.5 узла курс в RMC — шум, ставим
  `hasBearing = false` (фильтр это уже умеет).
- Точности скорости/курса в NMEA нет → `hasSpeedAccuracy = false`; фильтр
  возьмёт свои значения по умолчанию.
- Строки длиннее 82 символов (NMEA 4.1+, `GNGNS`, proprietary) не отбрасывать
  по длине — только по чексумме.

### 3.2 UBX (u-blox, опционально, большой выигрыш в качестве)

u-blox — самые распространённые чипы в USB-приёмниках. Сообщение
**`UBX-NAV-PVT`** содержит всё сразу: время, позицию, `hAcc`, скорость в NED,
`sAcc` (точность скорости), `headMot` + `headAcc` (точность курса), флаги
валидности. Это ровно то, что фильтр Калмана сейчас получает от Fused-провайдера
телефона (`speed_accuracy`, `bearing_accuracy`), и чего нет в NMEA.

Включение:
- M8 и старше: `UBX-CFG-MSG` (класс 0x01, id 0x07, rate 1) + `UBX-CFG-RATE`
  (период измерения, например 100–200 мс для 5–10 Гц).
- M9/M10/F9: `UBX-CFG-VALSET` с ключами `CFG-MSGOUT-UBX_NAV_PVT_USB`,
  `CFG-RATE-MEAS`.
- Определить u-blox: VID `0x1546`, либо ответ на `UBX-MON-VER`.
- Конфигурацию писать только в RAM-слой (не во flash), чтобы не «портить»
  приёмник пользователю.

### 3.3 Команды других производителей для повышения частоты (опционально)

- MediaTek/Airoha: `$PMTK220,200*2C` (5 Гц), `$PAIR050,...` для новых чипов.
- Quectel LC29H/L76: `$PQTMCFGFIXRATE` / PMTK.
- SiRF: переключение в NMEA при необходимости.

Делать это стоит по явной опции «Повысить частоту приёмника», т.к. многие
дешёвые модули на 9600 бод физически не успевают выдавать 10 Гц полного
набора NMEA.

## 4. Скорость порта (бод)

Для CDC-ACM скорость обычно игнорируется устройством. Для мостов
(PL2303/CP210x/FTDI/CH34x) она критична. Типичные значения:

| Бод | Где встречается |
|---|---|
| 4800 | SiRF (BU-353S4), старые приёмники — стандарт NMEA |
| 9600 | u-blox по умолчанию, ATGM336H, большинство модулей |
| 38400 | некоторые u-blox/MTK после настройки |
| 115200 | Quectel LC29H, RTK-приёмники, MTK на 10 Гц |
| 57600, 19200, 230400, 460800 | реже |

**Автоопределение**: перебирать скорости в порядке 9600 → 4800 → 115200 →
38400 → 57600 → 19200 → 230400, на каждой ~1.5–2 с слушать поток; скорость
принята, если пришло ≥ 2 строки NMEA с верной чексуммой (или валидный
UBX-кадр). Найденную скорость запоминать **по VID:PID+serial** и пробовать
первой при следующем подключении. В настройках — «Авто» или ручной выбор.

## 5. Разрешение USB и автозапуск — главная ловушка для магнитол

- `UsbManager.requestPermission()` показывает диалог при каждом подключении и
  **не переживает перезагрузку/переподключение**. На магнитоле, где питание USB
  пропадает при каждом выключении зажигания, это неприемлемо.
- Правильный путь — **intent-filter `USB_DEVICE_ATTACHED` на Activity** +
  `res/xml/usb_device_filter.xml`. Система сама предлагает открыть наше
  приложение, и если пользователь отметит «Использовать по умолчанию для
  этого USB-устройства», разрешение выдаётся **автоматически при каждом
  подключении**, а приложение запускается само — это заодно бесплатный
  автозапуск в USB-режиме.
- Фильтр `USB_DEVICE_ATTACHED` должен висеть на **Activity** (на Service/Receiver
  не работает). Делаем прозрачную activity-трамплин (`UsbAttachActivity`,
  `Theme.Translucent.NoTitleBar`, `excludeFromRecents`), которая стартует
  `GNSSClientService` и сразу `finish()`. Старт foreground-сервиса из activity
  не попадает под ограничения фонового запуска Android 12+.
- Состав фильтра — компромисс между «ловить всё» и «не всплывать на каждую
  флешку»:

```xml
<!-- res/xml/usb_device_filter.xml -->
<resources>
    <!-- Нативные CDC-ACM (u-blox, STM32 VCP, CH9102, ...) -->
    <usb-device class="2" />                       <!-- Communications device class -->
    <usb-device vendor-id="5446" />                <!-- 0x1546 u-blox, любой PID -->
    <!-- USB-UART мосты -->
    <usb-device vendor-id="1659" product-id="8963" />   <!-- 067b:2303 PL2303 -->
    <usb-device vendor-id="4292" product-id="60000" />  <!-- 10c4:ea60 CP210x -->
    <usb-device vendor-id="1027" product-id="24577" />  <!-- 0403:6001 FT232R -->
    <usb-device vendor-id="1027" product-id="24597" />  <!-- 0403:6015 FT231X -->
    <usb-device vendor-id="6790" product-id="29987" />  <!-- 1a86:7523 CH340 -->
    <usb-device vendor-id="6790" product-id="21972" />  <!-- 1a86:55d4 CH9102 -->
    <!-- …остальные PID из таблицы §1 -->
</resources>
```

  Минус фильтра по VID мостов: подключение любого Arduino-подобного
  устройства тоже предложит наше приложение. Это приемлемо — приложение
  проверит поток на NMEA и тихо закроется, если это не GNSS.
- Если устройства нет в фильтре, работает обычный путь: пользователь в
  настройках жмёт «Найти USB-приёмник» → список из `UsbSerialProber` +
  «все USB-устройства» → `requestPermission()` (с `PendingIntent.FLAG_MUTABLE`
  на Android 12+).
- Манифест: `<uses-feature android:name="android.hardware.usb.host" android:required="false"/>`.
- Отключение: runtime-ресивер `UsbManager.ACTION_USB_DEVICE_DETACHED` →
  остановить источник, ждать повторного подключения (магнитола часто
  переинициализирует USB-хаб при запуске, устройство может «моргнуть»).

## 6. Как это ложится на текущую архитектуру клиента

Сейчас `GNSSClientService` смешивает две вещи:

1. **Транспорт** — UDP-сокет, HELLO, `receiveLoop`, `handlePacket`, состояние
   соединения в `ConnectionManager`, старт/стоп по Wi-Fi `NetworkCallback`.
2. **Конвейер обработки** — `handleLocationUpdate` (дедупликация, компенсация
   задержки, predict/update Калмана) → `smoothingTick` 10 Гц → `injectSmoothed`
   → `MockLocationManager`.

Конвейер (2) от источника не зависит — его надо оставить как есть, а
транспорт вынести за интерфейс.

### 6.1 Интерфейс источника

```java
/** Источник GNSS-фиксов для конвейера фильтра. Все колбэки — на главном потоке. */
interface LocationSource {
    interface Listener {
        /** Новый фикс. Формат — существующий protobuf LocationUpdate. */
        void onFix(LocationProto.LocationUpdate fix, int satellites);
        /** Статус без фикса (поиск спутников, нет данных) + число спутников. */
        void onStatus(LocationProto.Status status, int satellites);
        /** Состояние «связи» с источником для UI/уведомления. */
        void onSourceState(ConnectionManager.ConnectionState state, String message, String detail);
    }
    void start(Listener listener);
    void stop(String reason);
}
```

Повторное использование `LocationProto.LocationUpdate` как внутреннего формата
фикса — самый дешёвый путь: `handleLocationUpdate` уже умеет всё (включая
`has*`-флаги для отсутствующей скорости/курса и точностей). NMEA/UBX-парсер
просто строит `LocationUpdate`:

- `timestamp` — время эпохи из RMC (дата+время UTC) → epoch millis.
  Это важно: дедупликация `fixTs == lastFedFixTimestampMs` и расчёт `dt`
  между фиксами уже опираются на это поле.
- `location_age` — для USB ≈ 0; реальную задержку USB-приёмника (обычно
  50–150 мс от эпохи до выдачи последнего предложения) покрывает уже
  существующая настройка `extraLatencyMs`. Для USB-режима разумно иметь своё
  значение по умолчанию (~100 мс). Сравнивать GNSS-время с часами магнитолы
  нельзя — часы магнитол часто неверны.
- `provider = "usb"` (или `"usb:u-blox"`), чтобы это было видно на мониторе.

### 6.2 Реализации

- `UdpServerSource` — перенос `startTransport/stopTransport/sendHelloTick/
  receiveLoop/handlePacket` из сервиса без изменения поведения.
- `UsbGnssSource`:
  - выбор устройства (`UsbSerialProber` + пользовательский `ProbeTable`),
    открытие порта, автоопределение бод (§4);
  - чтение через `SerialInputOutputManager` (отдельный поток библиотеки) →
    сборщик строк/UBX-кадров → парсер эпох → `post` на главный поток;
  - `onSourceState`: `CONNECTING` = порт открыт, ищем NMEA / нет фикса;
    `CONNECTED` = идут валидные фиксы; `DISCONNECTED` = устройство отключено;
  - watchdog: нет валидных данных N секунд → переоткрыть порт / вернуться к
    автоопределению скорости.
- Парсеры — чистая Java без Android-зависимостей (`NmeaParser`,
  `NmeaEpochAssembler`, `UbxParser`), чтобы покрыть их обычными JUnit-тестами,
  как сейчас `LocationKalmanFilterTest`. Тест-данные — реальные логи
  разных приёмников (u-blox, SiRF, MTK, Quectel).

### 6.3 Режимы и жизненный цикл сервиса

`Preferences.sourceMode`: `SERVER` | `USB` (и, опционально позже, `AUTO`).

| | Режим «Сервер» | Режим «USB» |
|---|---|---|
| Старт источника | Wi-Fi `onAvailable` (как сейчас) | `USB_DEVICE_ATTACHED` / приёмник уже подключён при старте сервиса |
| Остановка | Wi-Fi `onLost` | `USB_DEVICE_DETACHED` |
| Автозапуск | JobScheduler по Wi-Fi, boot, a11y | activity-трамплин по подключению USB, boot, a11y |
| Wi-Fi callback | нужен | не нужен (не регистрировать) |

`AUTO` (резерв): USB, если подключён приёмник с валидным фиксом; иначе сервер;
переключение с гистерезисом (например, USB без фикса > 10 с → сервер). При
переключении — `kalman.reset()` (у источников разные смещения и задержки).

Тип foreground-сервиса остаётся `location` — mock-провайдер требует именно
его; дополнительный `connectedDevice` не нужен.

`MockLocationManager` не меняется вообще.

### 6.4 UI

- Настройки: радиогруппа «Источник данных: Сервер (телефон) / USB-приёмник»
  (готовый `row_setting_radio`), блок USB: устройство, скорость (Авто/список),
  «Повысить частоту приёмника», «Найти USB-приёмник».
- Экран подключения/монитор: вместо адреса сервера — «u-blox 7 (1546:01a7),
  9600 бод, NMEA», число спутников из GGA/GSV, SNR в `SatelliteBarsView`,
  частота эпох.
- Тексты статусов в `strings.xml` и `values-ru/strings.xml`.

## 7. Риски и ограничения

- **Питание**: часть магнитол даёт мало тока на USB; активные антенны + модуль
  обычно < 100 мА — укладываются.
- **Хабы/«моргание» USB** при старте магнитолы — нужен повтор открытия порта,
  а не ошибка.
- **Порт занят прошивкой**: некоторые магнитолы сами открывают известные
  USB-GPS. `claimInterface(force=true)` отбирает интерфейс у ядерного драйвера,
  но не у другого userspace-процесса — тогда показываем понятную ошибку.
- **Холодный старт** USB-приёмника без A-GPS: 30 с – несколько минут на
  первый фикс. Это нормально, но в UI нужен статус «Поиск спутников (n)».
- **Антенна внутри салона** — точность хуже, чем у телефона у лобового стекла;
  честная оценка точности (GST/hAcc) важна, чтобы Калман правильно взвешивал.
- **Неподдерживаемые**: Garmin USB-протокол, приёмники только с SiRF binary.

## 8. План реализации (по этапам, каждый — отдельный PR)

1. **Рефакторинг без изменения поведения**: `LocationSource` +
   `UdpServerSource`, сервис работает через интерфейс. Существующие тесты
   зелёные.
2. **NMEA**: `NmeaParser` + `NmeaEpochAssembler` + юнит-тесты на логах
   разных приёмников (чексуммы, talker'ы, эпохи, GST/HDOP-точность, пустые поля).
3. **USB-источник**: зависимость usb-serial-for-android, `UsbGnssSource`,
   автоопределение бод, attach/detach, activity-трамплин + `usb_device_filter.xml`,
   ручной выбор устройства и запрос разрешения.
4. **Режимы и UI**: `Preferences.sourceMode`, переключатель в настройках,
   жизненный цикл сервиса по режиму, статусы на мониторе, локализация.
5. **Качество (опционально)**: UBX-NAV-PVT для u-blox, повышение частоты
   (UBX/PMTK/PAIR), режим `AUTO` с переключением, отладочный источник
   «воспроизвести NMEA-лог из файла» (удобно для тестов фильтра без машины).

Итог по охвату: USB Host API + usb-serial-for-android (CDC-ACM, PL2303, CP210x,
FTDI, CH34x) + NMEA с автоопределением скорости покрывает практически все
продаваемые USB GNSS-приёмники без root; UBX даёт заметный прирост качества
на самом популярном семействе (u-blox).
