# LocSync — для разработчиков

Пользовательское описание — в [README](../README.md). Здесь — устройство
системы, протокол, сборка и релизы.

## Модули

- `server-app` — приложение для телефона (сервер).
- `client-app` — приложение для магнитолы (клиент).
- `shared` — общие утилиты, UI-компоненты и класс `Protocol` (UDP-формат).
- `proto` — protobuf-схема `location.proto`, компилируется в оба приложения.

## Как это работает

```
┌─────────────────────────┐         Wi-Fi-хотспот          ┌──────────────────────────┐
│  Телефон (Server)        │         (UDP, порт 8887)       │  Магнитола (Client)       │
│                          │                                │                           │
│  Fused / GPS Location    │  ──── RESPONSE (protobuf) ───▶ │  Приём датаграмм          │
│  Foreground Service      │                                │  Фильтр Калмана           │
│  DatagramSocket          │  ◀──── HELLO (1 Гц) ─────────  │  MockLocationManager      │
└─────────────────────────┘                                └──────────────────────────┘
```

1. Телефон раздаёт Wi-Fi-хотспот, магнитола к нему подключается.
2. Клиент рассылает broadcast-пакет `HELLO` (1 раз в секунду) — так сервер
   узнаёт адрес клиента, IP настраивать не нужно.
3. Сервер шлёт клиенту `RESPONSE` с координатами в формате protobuf на каждый
   фикс; без новых фиксов — keepalive раз в 1,5 с с обновлённым возрастом.
4. Клиент сглаживает трек фильтром Калмана, компенсирует задержку и выдаёт
   позицию в систему как mock-провайдер GPS с частотой 10 Гц.

## Протокол (UDP)

Транспорт — UDP на порту **8887**. Каждый пакет:

```
[version:1 байт][type:1 байт][payload...]
```

- Текущая версия протокола — **3**. При несовпадении версий сервер отвечает
  `VERSION_MISMATCH`, и клиент показывает понятную ошибку.
- Типы пакетов: `HELLO` (0x01), `RESPONSE` (0x02), `VERSION_MISMATCH` (0x03).
- Максимальный размер пакета — 2048 байт.
- `payload` пакета `RESPONSE` — protobuf-сообщение `ServerResponse`
  (`proto/location.proto`): статус, число спутников и `LocationUpdate`
  (широта, долгота, высота, точность, курс, скорость, провайдер, возраст
  фикса, точности скорости и курса).

Живость соединения определяется по свежести датаграмм, а не по явным
подтверждениям: если пакетов давно не было, соединение считается разорванным.
Все таймауты — по монотонным часам (`SystemClock.elapsedRealtime`).

## Технические решения

- **UDP, а не TCP.** Один клиент в локальной сети, потеря отдельного пакета
  некритична — через секунду придёт новый. Нет переподключений, машины
  состояний сокета и кадрирования; меньше задержка.
- **Обнаружение без настройки.** `HELLO` уходит broadcast-ом на
  `255.255.255.255`, адрес сервера клиент узнаёт из ответа.
- **Автозапуск клиента.** Устойчивая задача `JobScheduler` на подключение к
  Wi-Fi (переживает перезагрузку) плюс запуск по boot. Дополнительно —
  «пустой» сервис специальных возможностей `AutostartAccessibilityService`:
  система поднимает его при каждой загрузке и после выгрузки процесса, что
  надёжнее `BOOT_COMPLETED` на магнитолах. Содержимое экрана он не читает.
- **Фильтр Калмана.** Модель с координированным поворотом, выход 10 Гц,
  компенсация задержки (возраст фикса + задержка Wi-Fi по `FixClock`),
  χ²-отсев выбросов, удержание на стоянке, адаптивные шумы процесса и
  измерений, поправка округления курса Fused. Все параметры — в настройках
  клиента.
- **Сервер.** Fused Location Provider (или чистый GPS), настраиваемый
  интервал и приоритет, GPS выключается после ухода клиента с задержкой,
  автозапуск/остановка по Bluetooth-устройствам машины.
- **protobuf-lite.** Формат описан один раз в `proto/location.proto`.

## Требования

- Сервер: Android 7.0 (API 24)+, Fused — Android 12+ с Google Play Services.
- Клиент: Android 9.0 (API 28)+.

## Сборка и тесты

```bash
./gradlew assembleDebug                                   # оба debug-APK
./gradlew :shared:testDebugUnitTest testDebugUnitTest     # юнит-тесты
```

Прогон фильтра на записанной поездке: `LOCSYNC_TRACK=/path/track-client.csv
./gradlew :client-app:testDebugUnitTest --tests '*TrackReplayTest'`.

**CI:** каждый push и PR собирают и тестируют проект и выкладывают оба
debug-APK как артефакт `debug-apks`. В debug-сборках внизу экрана показывается
`Version <ветка>-<shortsha>`.

## Релизы

Релиз собирается и публикуется `.github/workflows/release.yml` — при push тега
`v*` или вручную (Actions → Release → Run workflow, указать тег, например
`v3.6.1`; тег создаётся при публикации). Имя тега становится `versionName`.

```bash
git tag v1.2.3
git push origin v1.2.3
```

### Настройка подписи (один раз)

Release-сборки подписываются keystore из секретов репозитория (alias `key0`,
один пароль для хранилища и ключа).

1. Создать keystore (хранить вне git — `*.jks` в `.gitignore`):
   ```bash
   keytool -genkeypair -v -keystore keystore.jks -alias key0 \
     -keyalg RSA -keysize 2048 -validity 10000 \
     -storepass 'PASSWORD' -keypass 'PASSWORD' \
     -dname "CN=LocSync, OU=Dev, O=LocSync, C=US"
   ```
2. Добавить секреты репозитория GitHub:
   - `KEYSTORE_BASE64` — `base64 -w0 keystore.jks`
   - `KEY_PASSWORD` — пароль из шага выше

> **Сохраните `keystore.jks` и пароль.** Без них обновления той же подписью
> выпускать не получится.
